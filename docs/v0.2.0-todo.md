# v0.2.0 release TODO

Scope: five text publishing platforms (Bluesky, Threads, X, Tumblr, and
LinkedIn), the public npm Worker package, and a thin deployment template.
Do not add more platforms during this release preparation.

This checklist records planned work, not authorization to publish, deploy,
post to social accounts, create remote repositories, or commit and push.
Those actions require explicit maintainer approval. Check items only after
verification; record relevant results alongside them.

The review now uses `grill-with-docs`, combining `grilling` and `domain-modeling`.
Decisions Q1-Q12 are recorded below; implementation waits for confirmation of
shared understanding. The glossary defines terms, ADRs explain durable trade-offs,
and this checklist tracks acceptance work rather than completed capabilities.

## Confirmed release decisions (Q1-Q12)

- Audience: developers self-hosting with manually configured credentials.
  No OAuth onboarding, dashboard, or managed service promise in this release.
- Platform status: live validation is required for official support. Bluesky
  and Threads must pass before release, including the new Bluesky SDK path.
  X, Tumblr, and LinkedIn may ship as experimental if not live-validated.
  README must state validation status and known limitations. No additional
  experimental feature flag: configuring credentials opts into that platform.
- Migration: provide a manual path from full-source deployment repositories,
  not an automatic migration tool. Preserve D1 data, resource bindings, API
  key, historical statuses, and pending tasks. A maintenance window may reject
  new requests and delay scheduled tasks until service resumes. Verify the
  concrete cutover procedure against the implementation; do not promise zero downtime.
- Delivery: prevent duplicate provider calls from normal duplicate queue
  messages. Do not promise cross-platform exactly-once delivery. Ambiguous
  outcomes require manual platform verification, not automatic retries.
  Never blindly reset in-flight publications to pending during migration.
- Maintenance admission control: add a minimal optional switch that rejects
  new post creation with HTTP `503`, while health checks and existing post queries
  remain available. Do not add required configuration or imply that the switch
  pauses Queue or Cron. Background cutover safety requires separate verification.
  After authentication succeeds, every `POST /v1/posts` returns `503` before
  creation or idempotency processing, including replay requests. GET queries
  remain available. After maintenance ends, clients retry with the original
  idempotency key and request body under the existing idempotency rules.
- Updates: pin exact package versions with a lockfile. Dependabot checks weekly
  and opens PRs; no automatic merging or silent production upgrades.
  Configuration, workflow, and template script changes remain manual upgrades
  documented in release notes. Do not add whole-repository upstream synchronization.
- Release sequence: publish `0.2.0-rc.1` under npm's `next` dist-tag first.
  Validate package installation, new deployments, and existing deployment
  migration before publishing `0.2.0`. Increment RC versions for fixes; never
  overwrite a published version. Publication still requires separate approval.

## 1. Validate the distributable

Code checks during the design review found that ambiguity is currently represented
as publication `status: "failed"` with `errorAmbiguous: true`, not a separate
top-level status. Preserve that distinction in documentation and future UI design.
No built-in HTTP maintenance rejection was found; the optional admission switch
is an accepted requirement, not an existing feature.

- [ ] Rerun `npm test`, `npm run check`, `npm run bundle`, and `npm run startup`.
- [ ] Run `npm run build:package` and pack `@syndroo/cloudflare-worker`.
- [ ] Install the local tarball in an isolated project; verify Worker imports,
      deployment commands, and packaged migrations without publishing or deploying.
- [ ] Check for unresolved workspace dependencies, experimental code, secrets,
      and account-specific resource IDs in the artifact.
- [ ] Verify Apache-2.0, NOTICE, and bundled third-party license obligations.
- [ ] Reassess the six previously reported high-severity dependency findings;
      fix them or document affected scope and the disposition of each finding.

## 2. Prepare the thin deployment template

- [ ] Confirm the status of `Syndroo/syndroo-deploy-template`; create it if
      needed, with approval.
- [ ] Keep only deployment configuration, pinned package dependencies, a
      lockfile, necessary scripts, and documentation.
- [ ] Keep platform credentials optional; require only `SYNDROO_API_KEY`
      globally and validate credentials for each selected platform.
- [ ] Configure weekly Dependabot package update PRs with exact versions and
      a lockfile, without automatic merging.
- [ ] Document new secrets, D1 migrations, and user configuration conflicts.
- [ ] Implement and test the optional maintenance admission switch: post creation
      returns `503`; health checks and authenticated post queries remain available;
      omitted configuration preserves normal operation. Keep existing authentication
      requirements and response shape. Verify Queue/Cron behavior separately.
- [ ] Verify maintenance blocks authenticated POST requests, including idempotent
      replays, before creation or idempotency processing. Verify that replay with
      the original key and body follows existing rules after maintenance ends.
