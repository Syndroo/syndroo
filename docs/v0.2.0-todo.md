# v0.2.0 release TODO

Scope: five text publishing platforms (Bluesky, Threads, X, Tumblr, and
LinkedIn), the public npm Worker package, and a thin deployment template.
Do not add more platforms during this release preparation.

This checklist records planned work, not authorization to publish, deploy,
post to social accounts, create remote repositories, or commit and push.
Those actions require explicit maintainer approval. Check items only after
verification; record relevant results alongside them.

Decisions Q1-Q12 are confirmed below. The glossary defines terms, ADRs explain
durable trade-offs, and this checklist separates verified local development from
remaining live validation and publication steps.

## Confirmed release decisions (Q1-Q12)

- Audience: developers self-hosting with manually configured credentials.
  No OAuth onboarding, dashboard, or managed service promise in this release.
- Platform status: live validation is required for official support. Bluesky
  and Threads must pass before release, including the new Bluesky SDK path.
  X, Tumblr, and LinkedIn may ship as experimental if not live-validated.
  README must state validation status and known limitations. No additional
  experimental feature flag: configuring credentials opts into that platform.
- Migration: provide a manual path from full-source deployment repositories,
  not an automatic migration tool. Preserve D1 data, resource bindings, API
  key, historical statuses, and pending tasks. A maintenance window may reject
  new requests and delay scheduled tasks until service resumes. Verify the
  concrete cutover procedure against the implementation; do not promise zero downtime.
- Delivery: prevent duplicate provider calls from normal duplicate queue
  messages. Do not promise cross-platform exactly-once delivery. Ambiguous
  outcomes require manual platform verification, not automatic retries.
  Never blindly reset in-flight publications to pending during migration.
- Maintenance admission control: add a minimal optional switch that rejects
  new post creation with HTTP `503`, while health checks and existing post queries
  remain available. Do not add required configuration or imply that the switch
  pauses Queue or Cron. Background cutover safety requires separate verification.
  After authentication succeeds, every `POST /v1/posts` returns `503` before
  creation or idempotency processing, including replay requests. GET queries
  remain available. After maintenance ends, clients retry with the original
  idempotency key and request body under the existing idempotency rules.
- Updates: pin exact package versions with a lockfile. Dependabot checks weekly
  and opens PRs; no automatic merging or silent production upgrades.
  Configuration, workflow, and template script changes remain manual upgrades
  documented in release notes. Do not add whole-repository upstream synchronization.
- Release sequence: publish `0.2.0-rc.1` under npm's `next` dist-tag first.
  Validate package installation, new deployments, and existing deployment
  migration before publishing `0.2.0`. Increment RC versions for fixes; never
  overwrite a published version. Publication still requires separate approval.

## 0. Verify and harden delivery reliability

These release gates come before distributable validation. The architecture review
identified static failure paths; local fault injection has now reproduced the
partial-commit cases below, not production incidents. Reproduce remaining paths
with deterministic tests before choosing the smallest fix. Do not defer
correctness fixes to the v0.3.0 architecture work or introduce a generic repository.

### Post and Publication consistency

- [x] Reproduce concurrent completion of two publications for one Post; verify
      an older aggregate cannot overwrite the correct final Post status.
- [x] Inject failures between publication updates and Post aggregate refreshes;
      verify stored statuses converge without requiring another platform publish.
- [x] Fix confirmed consistency gaps within D1 operations. Keep aggregate reads
      and writes consistent with publication transitions; merely batching a write
      computed from an earlier read is not sufficient.

Original evidence: `src/repository.ts` updated publications and refreshed Post
status separately, reading counts before writing the derived status later.
State transitions now use D1 batches with a SQL aggregate computed within the
transaction. Stale recovery commits per Post, rechecking the stale predicate.
Concurrent terminal outcomes and a deterministic stale-read interleaving are
covered. The same barrier fails against the previous HEAD implementation
(`publishing` instead of `published`) and passes against the transactional code.

### Claim and persistence failure paths

- [x] Inject failure after the claim update succeeds but before its aggregate
      refresh or publication read completes. Record whether a provider call occurred.
- [x] Prevent auxiliary work from unnecessarily stranding an unsent publication
      in `publishing`, while preserving atomic claim and conservative handling
      when the claim outcome itself is unknown. Never blindly reset to `pending`.
- [x] Verify provider success followed by persistence failure cannot cause blind
      republication. Verify provider failure followed by persistence failure too.

Original evidence: `claimPublication` updated status and attempts, refreshed the
Post, and read the publication in separate awaited operations. These now execute
in one transaction. Database statement failure rolls back the claim; an unknown
commit outcome still follows the conservative infrastructure-retry path.

### First implementation evidence (2026-09-11)

- `test/jobs.spec.ts`: three added Queue tests with controlled Threads responses

### Orchestration regression coverage

- [x] Retry classification: only explicitly retryable, unambiguous failures retry;

- [x] Ambiguous outcome: no automatic republication after timeout or unknown result.
- [x] Enqueue failure: pending work is recovered through the actual Cron path.
- [x] Stale publishing: recovery preserves ambiguity and updates the Post correctly.
- [x] Concurrent idempotent creation: identical keys and requests create one Post;

- [x] Exercise real orchestration with controlled provider outcomes and D1 failure
      injection; adapter-only tests do not satisfy these gates.

### Retry timing contract

- [x] Reproduce a duplicate message arriving after a retryable failure changes
      the publication to `pending`, but before the delayed retry is due.
- Decision (2026-09-15): backoff is a strict earliest retry time, not best-effort.
- [x] Selected strict backoff: retry eligibility is persisted and enforced in both
      claim and Cron selection, with a new migration and regression tests.

Implementation evidence (2026-09-15):

- `migrations/0003_retry_timing.sql` adds nullable `publications.retry_at`; rows
  written before it stay `NULL` and immediately eligible. Apply migrations before
  deploying this Worker version. Older Worker code against the migrated database
  still publishes but cannot enforce the stored deadline.
- `src/retry.ts` holds the shared policy: a maximum of three application attempts,
  60 seconds after the first failure, 120 seconds after the second, and no retry
  for ambiguous outcomes.
- `markFailed` writes status, error fields, retry deadline, and the Post aggregate
  in one D1 batch; `retry: true` without an explicit deadline derives it from the
  stored attempt count. `markPublished` and terminal failures clear the deadline.
- Claim and pending Cron selection require `retry_at IS NULL OR retry_at <= now`.
  A duplicate Queue message before the deadline calls no provider and increments no
  attempt; the delivery is rescheduled for the remaining whole seconds instead of
  being acknowledged. A lost Queue retry is still recovered by the next Cron scan.
- `test/retry-timing.spec.ts`: eight local D1/Queue tests with a controlled
  Date-only clock. They cover one millisecond before and exactly at the boundary,
  Cron before and after due, duplicate delivery, concurrent claims at the boundary, transaction rollback of
  status plus deadline, the three-attempt cap, legacy `retry_at IS NULL` rows, and
  absence of the internal field from the public post response.
- Migration preservation was verified independently in isolated in-memory SQLite:
  migrations 0001 and 0002 applied, five posts and five publication states inserted
  with idempotency keys, ambiguity flags, and external IDs, then 0003 applied. All
  prior fields were identical, all five `retry_at` values were `NULL`,
  `foreign_key_check` returned no rows, and `integrity_check` was `ok`.

Acceptance: demonstrate the invariants above under controlled concurrency and
partial failure, rerun the relevant release checks, and record evidence. Keep the
existing HTTP contract and published migrations unless a separately reviewed change
is necessary. Broader internal restructuring belongs in [v0.3.0](v0.3.0-todo.md).
