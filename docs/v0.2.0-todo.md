# v0.2.0 release TODO

Scope: five text publishing platforms (Bluesky, Threads, X, Tumblr, and
LinkedIn), the public npm Worker package, and a thin deployment template.
Do not add more platforms during this release preparation.

This checklist records planned work, not authorization to publish, deploy,
post to social accounts, create remote repositories, or commit and push.
Those actions require explicit maintainer approval. Check items only after
verification; record relevant results alongside them.

The review now uses `grill-with-docs`, combining `grilling` and `domain-modeling`.
Decisions Q1-Q12 are recorded below; implementation waits for confirmation of
shared understanding. The glossary defines terms, ADRs explain durable trade-offs,
and this checklist tracks acceptance work rather than completed capabilities.

## Confirmed release decisions (Q1-Q12)

- Audience: developers self-hosting with manually configured credentials.
  No OAuth onboarding, dashboard, or managed service promise in this release.
- Platform status: live validation is required for official support. Bluesky
  and Threads must pass before release, including the new Bluesky SDK path.
  X, Tumblr, and LinkedIn may ship as experimental if not live-validated.
  README must state validation status and known limitations. No additional
  experimental feature flag: configuring credentials opts into that platform.
- Migration: provide a manual path from full-source deployment repositories,
  not an automatic migration tool. Preserve D1 data, resource bindings, API
  key, historical statuses, and pending tasks. A maintenance window may reject
  new requests and delay scheduled tasks until service resumes. Verify the
  concrete cutover procedure against the implementation; do not promise zero downtime.
- Delivery: prevent duplicate provider calls from normal duplicate queue
  messages. Do not promise cross-platform exactly-once delivery. Ambiguous
  outcomes require manual platform verification, not automatic retries.
  Never blindly reset in-flight publications to pending during migration.
- Maintenance admission control: add a minimal optional switch that rejects
  new post creation with HTTP `503`, while health checks and existing post queries
  remain available. Do not add required configuration or imply that the switch
  pauses Queue or Cron. Background cutover safety requires separate verification.
  After authentication succeeds, every `POST /v1/posts` returns `503` before
  creation or idempotency processing, including replay requests. GET queries
  remain available. After maintenance ends, clients retry with the original
  idempotency key and request body under the existing idempotency rules.
- Updates: pin exact package versions with a lockfile. Dependabot checks weekly
  and opens PRs; no automatic merging or silent production upgrades.
  Configuration, workflow, and template script changes remain manual upgrades
  documented in release notes. Do not add whole-repository upstream synchronization.
- Release sequence: publish `0.2.0-rc.1` under npm's `next` dist-tag first.
  Validate package installation, new deployments, and existing deployment
  migration before publishing `0.2.0`. Increment RC versions for fixes; never
  overwrite a published version. Publication still requires separate approval.

## 0. Verify and harden delivery reliability

These release gates come before distributable validation. The architecture review
identified static failure paths, not reproduced production incidents. Reproduce
them with deterministic tests before choosing the smallest fix. Do not defer
correctness fixes to the v0.3.0 architecture work or introduce a generic repository.

### Post and Publication consistency

- [ ] Reproduce concurrent completion of two publications for one Post; verify
      an older aggregate cannot overwrite the correct final Post status.
- [ ] Inject failures between publication updates and Post aggregate refreshes;
      verify stored statuses converge without requiring another platform publish.
- [ ] Fix confirmed consistency gaps within D1 operations. Keep aggregate reads
      and writes consistent with publication transitions; merely batching a write
      computed from an earlier read is not sufficient.

Evidence: `src/repository.ts` in the Worker package updates publications and
refreshes Post status separately; `refreshPostStatus` reads counts before writing
the derived status in a later operation.

### Claim and persistence failure paths

- [ ] Inject failure after the claim update succeeds but before its aggregate
      refresh or publication read completes. Record whether a provider call occurred.
- [ ] Prevent auxiliary work from unnecessarily stranding an unsent publication
      in `publishing`, while preserving atomic claim and conservative handling
      when the claim outcome itself is unknown. Never blindly reset to `pending`.
- [ ] Verify provider success followed by persistence failure cannot cause blind
      republication. Verify provider failure followed by persistence failure too.

Evidence: `claimPublication` currently updates status and attempts, refreshes the
Post, and reads the publication in separate awaited operations; `jobs.ts` handles
an exception from this sequence as an infrastructure retry.

### Orchestration regression coverage

- [ ] Duplicate delivery: normal duplicate Queue messages cause one provider call.
- [ ] Retry classification: only explicitly retryable, unambiguous failures retry;
      application attempts remain capped at three.
- [ ] Ambiguous outcome: no automatic republication after timeout or unknown result.
- [ ] Enqueue failure: pending work is recovered through the actual Cron path.
- [ ] Stale publishing: recovery preserves ambiguity and updates the Post correctly.
- [ ] Concurrent idempotent creation: identical keys and requests create one Post;
      conflicting requests preserve the existing conflict response.
- [ ] Exercise real orchestration with controlled provider outcomes and D1 failure
      injection; adapter-only tests do not satisfy these gates.

### Retry timing contract

- [ ] Reproduce a duplicate message arriving after a retryable failure changes
      the publication to `pending`, but before the delayed retry is due.
- [ ] Decide and document whether backoff is best-effort or a strict earliest
      retry time. The review does not authorize choosing either silently.
- [ ] If strict backoff is selected, persist retry eligibility and enforce it in
      both claim and Cron selection, with a new migration and regression tests.
      If best-effort is retained, document the limitation and verify the attempt cap.

Acceptance: demonstrate the invariants above under controlled concurrency and
partial failure, rerun the relevant release checks, and record evidence. Keep the
existing HTTP contract and published migrations unless a separately reviewed change
is necessary. Broader internal restructuring belongs in [v0.3.0](v0.3.0-todo.md).

## 1. Validate the distributable

Code checks during the design review found that ambiguity is currently represented
as publication `status: "failed"` with `errorAmbiguous: true`, not a separate
top-level status. Preserve that distinction in documentation and future UI design.
No built-in HTTP maintenance rejection was found; the optional admission switch
is an accepted requirement, not an existing feature.

- [ ] Rerun `npm test`, `npm run check`, `npm run bundle`, and `npm run startup`.
- [ ] Run `npm run build:package` and pack `@syndroo/cloudflare-worker`.
- [ ] Install the local tarball in an isolated project; verify Worker imports,
      deployment commands, and packaged migrations without publishing or deploying.
- [ ] Check for unresolved workspace dependencies, experimental code, secrets,
      and account-specific resource IDs in the artifact.
- [ ] Verify Apache-2.0, NOTICE, and bundled third-party license obligations.
- [ ] Reassess the six previously reported high-severity dependency findings;
      fix them or document affected scope and the disposition of each finding.

## 2. Prepare the thin deployment template

- [ ] Confirm the status of `Syndroo/syndroo-deploy-template`; create it if
      needed, with approval.
- [ ] Keep only deployment configuration, pinned package dependencies, a
      lockfile, necessary scripts, and documentation.
- [ ] Keep platform credentials optional; require only `SYNDROO_API_KEY`
      globally and validate credentials for each selected platform.
- [ ] Configure weekly Dependabot package update PRs with exact versions and
      a lockfile, without automatic merging.
- [ ] Document new secrets, D1 migrations, and user configuration conflicts.
- [ ] Implement and test the optional maintenance admission switch: post creation
      returns `503`; health checks and authenticated post queries remain available;
      omitted configuration preserves normal operation. Keep existing authentication
      requirements and response shape. Verify Queue/Cron behavior separately.
- [ ] Verify maintenance blocks authenticated POST requests, including idempotent
      replays, before creation or idempotency processing. Verify that replay with
      the original key and body follows existing rules after maintenance ends.

## 3. Validate live publishing (approval required)

- [ ] Bluesky: official SDK publishing and URL facets.
- [ ] Threads: regression test the existing native HTTP adapter.
- [ ] X: OAuth credentials, application permissions, and text publishing.
- [ ] Tumblr: target blog, OAuth signing, and text publishing.
- [ ] LinkedIn: author permissions, API version, text escaping, and publishing.
- [ ] Record live validation evidence and label unvalidated platforms experimental
      in README. Bluesky and Threads passing is a release gate; the other three
      may remain experimental without blocking release.
- [ ] Verify multi-platform publishing, content overrides, scheduled delivery,
      and status queries.
- [ ] Verify idempotent requests do not duplicate posts; use controlled tests
      for failure classification and retry behavior, including ambiguous results.

      single release version source.
- [ ] Turn the relevant Unreleased changelog entries into v0.2.0 release notes.
- [ ] Update README and the release guide's first-release bootstrap references

- [ ] Document platform limits, credentials, compatibility, and upgrade steps.
- [ ] Verify npm publication permissions, two-factor authentication, and the

- [ ] Confirm final CI passes, run `git diff --check`, and review the diff.

## 5. Publish and validate deployment (separate approvals required)

- [ ] Bootstrap `@syndroo/cloudflare-worker@0.2.0-rc.1` on npm under `next`
      from the reviewed candidate commit with two-factor authentication.
- [ ] Configure npm Trusted Publishing for later releases.
- [ ] Install the published package in the template and commit its lockfile.
- [ ] Validate Deploy to Cloudflare: resource creation, migrations, startup,
      and publishing.
- [ ] Validate an existing deployment's upgrade path; distinguish code rollback
      from database recovery and document their limits. Verify maintenance-mode
      request rejection, preservation of data and credentials, resumed scheduled
      tasks, and safe handling of in-flight and ambiguous publications.
- [ ] Publish new RC versions if fixes are needed; repeat affected acceptance checks.
- [ ] After RC acceptance, rerun release checks and publish `0.2.0` under
      `latest` from the reviewed final release commit.
- [ ] Pin the template to `0.2.0`, refresh its lockfile, and verify the final artifact.
- [ ] Switch the main repository's Deploy button to the validated template.
- [ ] Create the matching `v0.2.0` tag and GitHub Release from the exact npm
      release commit. Confirm the workflow skips the already published version.
