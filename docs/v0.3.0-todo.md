# v0.3.0 architecture TODO

Goal: improve data-model clarity, publishing orchestration, and testability through
small interfaces that hide meaningful complexity. Do not rewrite the application
or add layers merely to reorganize files.

This is a planning checklist, not authorization to implement, change public
contracts, publish, deploy, or commit and push. Reliability defects remain
[v0.2.0 release gates](v0.2.0-todo.md), not deferred refactoring work.

## 1. Establish the baseline and select changes

- [ ] Start from the accepted v0.2.0 behavior and reliability regression suite.
- [ ] Map the current HTTP, Post creation, publishing, persistence, and recovery
      interfaces, including caller ordering requirements and failure semantics.
- [ ] For each proposed refactor, identify concrete duplicated knowledge, change
      spread, or testing friction. Skip changes without a demonstrated benefit.
- [ ] Record the selected scope, compatibility requirements, and stop conditions
      before implementation. Use ADRs only for durable, non-obvious trade-offs.

## 2. Clarify data models and external contracts

- [ ] Classify Post and Publication fields as business facts, execution bookkeeping,
      persisted representations, or externally exposed information.
- [ ] Specify which existing HTTP fields are compatibility commitments. Do not
      remove fields just because they also serve internal execution.
- [ ] Introduce separate query representations or internal models only where
      they resolve an actual difference; avoid identical DTOs and mapping layers.
- [ ] Preserve the distinction between confirmed failure and ambiguous outcome.
      Do not silently replace `failed` plus `errorAmbiguous` with a new API status.
- [ ] Test stored-data mapping and HTTP output compatibility against the baseline.

## 3. Simplify publishing orchestration

- [ ] Evaluate a small publishing-execution Module that can be exercised without
      constructing a Cloudflare Queue batch for every business-behavior test.
- [ ] Keep Queue acknowledgment and retry mechanics in the Cloudflare implementation;
      expose only the execution results and dependencies callers genuinely need.
- [ ] Test through the resulting Interface with controlled provider outcomes and
      real D1 integration coverage for atomic operations.
- [ ] Preserve atomic claims, attempt limits, ambiguity handling, enqueue recovery,
      and the agreed retry timing contract. Do not introduce a DI container.

## 4. Clarify rule ownership without weakening atomicity

- [ ] Identify reusable pure rules for status aggregation and retry decisions;
      extract them only where this improves locality or independent verification.
- [ ] Keep atomic claim, conditional writes, and consistency enforcement inside
      the concrete D1 implementation. Never replace them with read-then-write logic.
- [ ] If SQL and pure rules express the same policy, add parity tests or keep a
      single authoritative implementation rather than allowing independent drift.
- [ ] Keep one concrete D1Repository unless a real second persistence implementation
      justifies a storage Interface. A large file alone is not sufficient reason.

## 5. Reduce duplicated platform metadata

- [ ] Compare platform configuration checks, publisher construction, and provider
      naming across `publishers.ts` and `posts.ts`.
- [ ] Consolidate duplicated facts where useful while retaining explicit platform
      selection and platform-specific credential validation.
- [ ] Preserve stored provider names unless a separately reviewed compatibility
      change is needed. No plugin registry or multi-layer adapter factory.
- [ ] Keep core and adapters private implementation details of the public Worker
      package; do not accidentally create new independently supported public APIs.

## 6. Verify and stop

- [ ] Land small independently verifiable changes, not a whole-repository rewrite.
- [ ] Prove HTTP, stored-data, and delivery behavior remain compatible after each
      refactor; add a new migration if a schema change is genuinely necessary.
- [ ] Run `npm test`, `npm run check`, `npm run bundle`, `npm run startup`,
      `npm run build:package`, and `git diff --check`.
- [ ] Install the packed Worker in an isolated consumer and verify template
      compatibility without depending on unpublished workspace packages.
- [ ] Compare caller complexity, duplicated policy, and test setup with the baseline;
      fewer or shorter files alone do not establish architectural improvement.
- [ ] Update relevant documentation and remove superseded implementation paths.

## Future triggers, not automatic v0.3.0 scope

- **Multiple accounts or OAuth:** design publishing targets, account ownership,
  credential lifecycle, and idempotency scope before implementation. The current
  one-publication-per-Post-and-platform constraint cannot represent multiple target
  accounts on the same platform without a deliberate model change.
- **Manual reconciliation UI:** decide what attempt history, verification evidence,
  and operator actions must be retained. The latest error is not an audit trail;
  no UI, retry endpoint, or event-sourcing framework is implied by this plan.
- **Second database:** design a storage seam around real required behavior, not
  generic CRUD. Preserve concurrency guarantees across implementations.
- **Second runtime:** consider runtime abstraction only when a concrete supported
  deployment target requires it; keep Cloudflare code outside core.
- Media, tenancy, additional platforms, and managed hosting remain separately
  scoped product work, not prerequisites for these internal improvements.
