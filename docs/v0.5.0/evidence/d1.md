   kind/payload version is never coerced and is filtered out of `listReady`,
   claim and recovery selectors.
3. **Winner snapshots** — CAS returns `expectedRevision + 1`; `acquireRefresh`
   returns the lease it wrote; callback claim returns the `exchanging`
   operation it wrote; `claimExecution` returns the snapshot built from its own
   pre-read plus its own claim identity; activation returns its own revision.
   A delegated `batch` wrapper injects a concurrent replacement before the
   result is returned and the winner still holds its own lease/attempt. A
   committed-then-thrown batch yields `unknown` for refresh and callback claims.
4. **Old DLQ guard** — the stale-publishing branch now also requires
   `current_job_id = input.jobId`; a late DLQ for a superseded job cannot
   terminate a newer attempt.
5. **Contract parity** — the create batch evaluates the caller's slot binding
   (not just the revision) and a mismatched binding writes nothing;
   `createAuthOperation` reports a duplicate as a contract error and an

## 4. Guarded-batch design

* Every mutation is one `D1Database.batch`; the winning statement writes a fresh
  private `mutation_marker` and every dependent statement matches that exact
  token, so a zero-row guard writes nothing without any post-commit JavaScript
  "rollback".
* Create gates the parent insert on all credential guards plus idempotency
  uniqueness; children select the parent id **and** the marker. A pre-existing
  post or job id returns a conflict before the batch, and a unique-constraint
  race inside the batch re-reads and replays the original receipt.
* Claim gates on current job/entity/kind/attempt number, publication state, due
  time, live transport intent (`status <> 'cancelled'`, `dlq_seen_at IS NULL`),
  attempt budget and the preparation-time slot revision; the aggregate update
  requires the same marker. A batch error returns `unknown`, which authorises no
  provider call.
* Outcome commits gate on claim token + attempt id + current job; successor
  jobs and job cancellation depend on the marker; identical replay returns
  `already_applied`, a different result conflicts, and the attempt budget cannot
  be extended.
* Activation gates operation phase/expiry/configuration/expected revision and
  the current slot revision in one statement, then writes the slot only while
  the operation marker is present. Completed replay returns the stored receipt
  revision.
* Refresh acquires a unique lease before any network step; an existing
  unfinished lease (live or expired) never yields a second acquisition
  (`lease_held` / `reconnect_required`), completion and failure require the
  exact lease token and revision, and target columns are only accepted when they
  match the stored connection.
* DLQ settlement verifies the entity pair before writing metadata, excludes
  DLQ-seen jobs from `listReady`, and settles both `pending` and `dispatched`
  future jobs at their due time. GC keeps unknown/ambiguous records and
  `cleanupExpired` uses one eligible union with a single budget.

## 5. D1-specific fixtures (6 tests)

1. **Zero-row guard**: a stale credential guard yields
   `credential_revision_mismatch` with `posts`, `publications` and `outbox_jobs`
   all empty.
2. **Trigger rollback**: a `BEFORE INSERT ON outbox_jobs` trigger aborting the
   batch leaves every table empty, and the same request succeeds afterwards.
3. **Claim race**: two concurrent claims produce exactly one winner; the loser
   reports `already_claimed`; attempts remain 1.
4. **Activation vs direct set**: exactly one concurrent write wins; the slot
   ends at revision 2.
5. **Uncertain claim**: a trigger aborting the aggregate update makes the claim
   return `unknown` with the publication still `pending` and `attempts = 0`; the
   next claim succeeds.
6. **Metrics and query plan**: after seeding 120 finished publications plus one
   live one, `claimExecution` reports its statement count and non-zero
   `changes`; `EXPLAIN QUERY PLAN` for the ready selector contains
   `idx_outbox_ready` and for the stalled selector `idx_outbox_recovery`;
   `collectFinished` respects `limit = 5`.
