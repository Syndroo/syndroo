# v0.3.0 architecture: selected scope and implementation record

Status: architecture implementation in the source tree. This is **not** a
release. `@syndroo/cloudflare-worker` stays `0.2.0-rc.1` and unpublished, the
repository root stays `0.1.0`, and nothing here is tagged, deployed, or
published. HTTP request and response shapes, status codes, the D1 schema, and
the stored provider names are unchanged.

This is a validated candidate baseline, not a fully accepted live release:
local gates, the Mock SNS gate, and the packaged template checks pass, while
live-account validation, registry publication, and the production cutover stay
open.

This record covers the selected part of [v0.3.0-todo.md](v0.3.0-todo.md). The
rest of that plan stays deferred; the checklist marks which items were
implemented, reviewed without change, or left open.

## Selected scope

Three concrete problems justified changes.

1. Publishing behavior could only be exercised through a Cloudflare Queue
   `MessageBatch`. Claim handling, failure classification, and retry decisions
   were observable only as Queue outcomes, so business-behavior tests had to
   build Queue messages to reach the code under test.
2. Provider naming existed only as a private `providerFor` switch in
   `src/posts.ts`, while platform configuration and publisher construction lived
   in `src/publishers.ts`. The installed-platform list was therefore written out
   in two files.
3. The plan asked for a data-model and compatibility record that did not exist.

Everything else in the plan was left alone: no new layer, no rewritten
repository, no schema change, no new public route.

## Publishing execution

`packages/cloudflare-worker/src/publishing.ts` owns claim, provider call,
failure classification, and success persistence, and returns only a decision:

```typescript
export type PublicationDecision =
  | { action: "ack" }
  | { action: "retry"; delaySeconds: number };

export async function executePublication(
  publicationId: string,
  repository: D1Repository,
  env: Env,
): Promise<PublicationDecision>;
```

The executor takes a `Publication` id, the concrete `D1Repository`, and `Env`.
It never receives or constructs a Queue message, so a test can drive it directly
with a real local D1 database and a controlled `fetch` double.
Acknowledgement and retry mechanics stay in `src/jobs.ts`, which validates the
job body, maps `retry` to `message.retry({ delaySeconds })` and `ack` to
`message.ack()`, and keeps the `invalid_publication_job` log for malformed
messages.

Behavior held constant by this extraction:

- one atomic claim per publication, with the attempt increment inside the claim
  transaction; a claim or claim-read failure retries the delivery after 60
  seconds without touching the provider;
- a duplicate delivery that finds a live claim is parked for the 15-minute
  stale-claim window, and one that finds a persisted `retry_at` waits for that
  stored instant;
- retry eligibility, attempt cap, ambiguity, and the earliest retry time are
  persisted in the same D1 transaction as the failure;
- a failure to persist a provider result retries the delivery after 60 seconds
  and leaves the publication claimed, so content is never resent on that path;
- log events keep their names and fields (`publication_published`,
  `publication_failed`, `publication_claim_failed`, `publication_read_failed`,
  `publish_failure_persist_failed`, `publish_success_persist_failed`).

`src/repository.ts` and its SQL are untouched.

## Provider naming

`providerFor(platform)` moved from `src/posts.ts` to `src/publishers.ts`, beside
`isPlatformConfigured` and `publisherFor`. Installed-platform configuration,
publisher construction, and provider naming are now maintained in one file, but
the switches remain distinct: naming never depends on credentials, while
construction validates them. This removes `posts.ts`'s own copy of the
installed-platform list and localizes future platform edits; it does not
introduce a registry or a shared metadata object, and the three switches still
list platforms separately.

`packages/cloudflare-worker/test/publishers.spec.ts` pins the stored names
(`bluesky-native`, `threads-native`, `x-sdk`, `tumblr-native`,
`linkedin-native`) and asserts that `providerFor(platform)` still equals
`publisherFor(platform, configuredEnv).name` for all five installed platforms,
so the two switches cannot drift silently. `mastodon` and `nostr` remain
recognized but not installed: `providerFor` reports `422
PLATFORM_NOT_CONFIGURED`, and `publisherFor` rejects them as unconfigured
because configuration is checked before the publisher switch.

## Data model classification

Post and Publication fields carry four different kinds of meaning. Rows in D1
are the persisted representation of all four; the classification below records
what each field is for, which fields are external commitments, and which field
stays internal.

| Field | Classification | Notes |
|---|---|---|
| `Post.id`, `Post.createdAt` | business fact, exposed | one logical publishing request |
| `Post.content` | business fact, exposed | shared text |
| `Post.platforms`, `Post.overrides` | business fact, exposed | target selection and per-platform text |
| `Post.scheduledAt` | business fact, exposed | requested publish time |
| `Post.status` | derived aggregate, exposed | computed from its publications in SQL, never set from a stale JS snapshot |
| `Publication.id`, `postId`, `platform`, `content` | business fact, exposed | one platform delivery and the text actually sent |
| `Publication.provider` | persisted representation, exposed | which adapter ran; stored data, not operator input |
| `Publication.status` | execution state machine, exposed | `scheduled`, `pending`, `publishing`, `published`, `failed` |
| `Publication.attempts` | execution bookkeeping, exposed | attempt count including the running claim |
| `Publication.externalId`, `externalUrl` | platform fact, exposed | only set from a provider response; never fabricated |
| `Publication.errorCode`, `errorMessage`, `errorAmbiguous` | execution outcome, exposed | `errorAmbiguous` distinguishes "may have been accepted" from confirmed failure |
| `Publication.scheduledAt` | business fact, exposed | copied from the Post schedule |
| `Publication.publishedAt` | execution timestamp, exposed | terminal success time |
| `Publication.enqueuedAt`, `publishingAt` | execution bookkeeping, exposed | Queue lease and claim timestamps |
| `Publication.createdAt` | business fact, exposed | row creation |
| `Publication.retryAt` (`StoredPublication.retryAt`) | execution bookkeeping, internal | persisted earliest retry time; gates claiming and Cron selection, never returned by the API |
| `Idempotency-Key` input and stored key | persisted representation, exposed as input | one key per logical Post; replay rules documented in the README |

Design consequences kept from v0.2.0:

- fields that serve internal execution are not removed from the HTTP response;
  `attempts`, `enqueuedAt`, and `publishingAt` stay compatibility commitments;
- no new DTO or mapping layer was added. `StoredPublication` remains the single
  internal extension of `Publication` (it adds `retryAt`), and
  `mapPublication` remains the one row-to-API mapping;
- `failed` plus `errorAmbiguous` stays the representation of an uncertain
  outcome. No new API status was introduced, and ambiguous results are never
  retried automatically;
- stored-data and HTTP output compatibility are covered by
  `test/retry-timing.spec.ts` (including a public-shape assertion that
  `retryAt` never appears in the HTTP response), `test/repository.spec.ts`, and
  `test/orchestration.spec.ts`.

## Deferred, not selected

Still open, with the reasons from the plan:

- multiple accounts or OAuth; the current model allows one publication per Post
  and platform and cannot represent a second target account on one platform;
- a manual reconciliation UI, attempt history, or an event backlog; the latest
  error is not an audit trail;
- a second database or a storage interface; one concrete `D1Repository` is
  still correct;
- a second runtime, media, tenancy, extra platforms, and managed hosting;
- extracting Post status aggregation into a pure rule; the aggregate is one SQL
  statement that computes from current rows inside the transaction, and a JS
  copy would create exactly the drift the plan warns about.

## Limits of this record

No live social account was contacted and no deployment, publish, or tag was
performed. No schema migration was added, and no remote database was touched:
the local test setup and the template rehearsal apply the existing migrations to
local D1 instances only. No performance, browser, or visual check is claimed.

This tree is a candidate baseline, not a fully accepted live release. Live
social-platform validation, npm publication, the registry-backed template
lockfile, CI on the published artifact, and the production cutover all remain
separate, explicitly authorized steps.
